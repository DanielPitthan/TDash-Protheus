Manual técnico

Para a equipe de TI e desenvolvedores AdvPL/TLPP: como instalar as APIs do TDash no Protheus, o que o app espera de cada rota e como mudar uma regra ou criar um indicador sem quebrar o app.

Requisitos

  • Protheus 12.1.2410 ou mais novo, com TLPP habilitado.
  • REST do AppServer ativo, com autenticação Basic e acessível pela internet (ou pela VPN dos celulares) em HTTPS. O app recusa http://.
  • TDS-VSCode (TOTVS Developer Studio for VS Code) para compilar no RPO.
  • Banco SQL Server, Oracle ou PostgreSQL. As consultas usam SQL portável e ChangeQuery.
  • Opcional: PowerShell 5.1+ para o smoke test.

Instalação

  1. Confira o ambiente. Protheus 12.1.2410+, REST do AppServer ativo com autenticação Basic e HTTPS.
  2. Compile no RPO, com o TDS-VSCode, nesta ordem:
    1. src/core/*.tlpp (os módulos dependem dele);
    2. src/fin, src/fat, src/com, src/est, src/pcp, src/fis, src/ctb, src/gpe;
    3. src/custom (depende de src/core e src/fat).
    Compile primeiro em homologação.
  3. Teste uma rota com curl. Nas rotas /core, envie x-erp-module: FAT: 
    curl -u USUARIO:SENHA -H "x-erp-module: FAT" https://<servidor>:<porta>/api/tdash/v1/core/branches
    Esperado: 200 com items (empresa, filial, nome, CNPJ). Senha errada: 401.
  4. Rode o smoke test para conferir todas as rotas de uma vez.
  5. Contabilidade e RH: rode os diagnósticos e combine com a contabilidade quais visões gerenciais usar, e com o RH quais verbas são hora extra.
  6. Parâmetros: crie no SX6 só os MV_TD… cujo padrão não serve.
  7. Confira os números de cada módulo contra os relatórios padrão, na mesma filial e período.
  8. Libere os módulos aos usuários no Configurador (acesso por módulo).
  9. Passe aos usuários o endereço do REST (ex.: https://cliente.protheus.cloudtotvs.com.br:1557/api) e o manual do usuário.

Codificação CP1252

O compilador do Protheus só aceita Windows-1252. No repositório os fontes ficam em UTF-8 (diff legível no GitHub); o .gitattributes faz o Git entregar em CP1252 com CRLF no checkout:

*.tlpp text eol=crlf working-tree-encoding=CP1252
*.prw  text eol=crlf working-tree-encoding=CP1252
*.th   text eol=crlf working-tree-encoding=CP1252

Baixou o .zip em vez de clonar? O GitHub entrega os arquivos em UTF-8. Antes de compilar, converta para Windows-1252 (no VS Code: Reabrir com codificação › UTF-8 e depois Salvar com codificação › Windows 1252). Acentos trocados (Ã§, Ã£) nas mensagens são sinal de arquivo em UTF-8. Não use caracteres fora do CP1252 (Σ, ≥, emojis), nem em comentários.

Smoke test

Depois de compilar, rode no PowerShell. A senha é pedida no terminal, não aparece e não é gravada:

.\tools\smoke-test.ps1 -BaseUrl "https://<cliente>.protheus.cloudtotvs.com.br:1557/api" -User "usuario" -Company "01" -Branch "D MG 01"
ParâmetroPara quê
-Module "FIN,PCP"Só as rotas destes módulos (CUSTOM testa os painéis de exemplo)
-IncomeView / -BalanceViewTesta a DRE e o Balanço com as visões do cliente
-OvertimeCodes "179,181"Testa as horas extras do RH
-CustomerCode / -SupplierCodeTesta a posição do cliente e do fornecedor
-OutDirPasta dos resultados (padrão .\smoke-results)
  • Cada resposta vai para um .json e o resumo para resumo.csv (status e tempo).
  • Esperado: 200 em todas, exceto os testes propositais de indicador inexistente (404) e de configuração ausente (422).
  • Se a primeira chamada devolver 401, o script para, para não bloquear o usuário.
  • Quando uma chamada de kpis devolve 500, o script repete um indicador por vez e mostra qual falhou.
  • A pasta de resultados tem dados do cliente: não versione nem envie por canais abertos.

Acesso por módulo

O app mostra só os módulos liberados na aba Menus do cadastro do usuário (SIGACFG › Usuário › Senhas › Usuários) e dos grupos dele. Para liberar um painel, libere o módulo e peça ao usuário para sair e entrar de novo.

  • Módulo marcado como sem acesso (X no menu) não aparece.
  • "Priorizar configuração do grupo" marcado: valem só os menus dos grupos.
  • É filtro de exibição: o REST do Protheus continua validando usuário, filial e módulo em cada chamada.
  • As rotas /core usam x-erp-module: FAT. Se o REST exigir o módulo do header, o usuário precisa ter o Faturamento liberado para entrar no app.
  • Para investigar, compile tools/diagnostico-acesso.tlpp e execute tdash.tools.u_tdAcessoDiag("login.do.usuario") pelo Configurador › Fórmulas.

Caminho de uma requisição

Exemplo: GET /tdash/v1/fin/kpis?ids=fin.receivable_open&dateFrom=20261001&dateTo=20261031&compare=prev

  1. O REST confere o Basic Auth (senha errada: 401, sem chegar ao TDash), troca para a filial do tenantid e abre o módulo do x-erp-module.
  2. O REST encontra a rota pela anotação @Get("/tdash/v1/fin/kpis") da classe TDashFinApi.
  3. getKpis() lê os parâmetros com TDashRequest, valida datas e comparação com TDashPeriod e confere cada id no catálogo com u_findIndicator. Erro: 400 ou 404 na hora.
  4. Dentro de TRY … CATCH, pede os valores ao repositório, monta cada cartão com u_kpiItem e define o Cache-Control pela validade do indicador.
  5. oRest:setResponse(oHelper:getResponse(jBody)) grava o JSON em UTF-8.
  6. Erro inesperado: o CATCH chama oHelper:serverError(...), que registra no log e responde 500 com mensagem genérica.

Convenções de código

  • TLPP tipado (local cNome := "" as character) com prefixo húngaro (c, n, l, d, a, j, o).
  • Só User Function e static function; rotas são métodos de classe com @Get.
  • Todo valor que vem da requisição entra por bind (?), nunca concatenado no SQL. Tabela por RetSqlName(), filial por FWxFilial() de cada tabela, sempre D_E_L_E_T_ = ' '.
  • Sem IIf() (SonarQube CA4000), sem data menos data (use tdash.core.u_daysBetween), sem as variant.
  • Sem return dentro de TRY … CATCH: valide e responda os erros antes do TRY.
  • Todo método tem cabeçalho Protheus.doc.

Segurança

  • Usuário, filial e módulo são validados pelo REST do Protheus antes da API; o TDash não repete a checagem.
  • Parâmetros: datas por u_parseDate, números por u_parseInt com faixa, códigos por u_isSafeCode (letras, dígitos, ponto, hífen e espaço), ids só do catálogo.
  • Erros nunca levam SQL, tabela ou pilha ao app: o detalhe vai para o console.log com FWLogMsg, grupo TDASH.
  • RH: só números agrupados, com o mínimo de pessoas de MV_TDMINGR (LGPD).

Rota kpis

{
  "items": [
    {
      "id": "fin.receivable_overdue",
      "title": "A receber vencido",
      "unit": "BRL",
      "direction": "down_is_good",
      "value": 1284300.55,
      "compare": { "mode": "prev", "value": 1150000.00, "deltaPct": 11.68 },
      "generatedAt": "2026-10-21T10:15:00",
      "ttl": 300
    }
  ]
}
  • Não mude o id de um indicador existente: é ele que liga o valor ao cartão da tela.
  • title, unit, direction e ttl vêm da API e aparecem no app sem atualizá-lo.
  • compare é null quando não há comparação; deltaPct é null quando a base é zero.
  • hidden: true mostra "—" e "Protegido pela LGPD".
  • Um id fora do catálogo faz a chamada inteira responder 404.

Regras gerais do JSON

  • UTF-8, nomes em camelCase, exatamente como no contrato.
  • Números como número JSON, não texto. Valores monetários e percentuais com 2 casas; percentual de 0 a 100 (8.4 = 8,4%).
  • Datas como AAAA-MM-DD; data/hora como AAAA-MM-DDThh:mm:ss.
  • Campos extras são ignorados pelo app. Campo obrigatório ausente ou de tipo errado mostra "Resposta inválida do servidor".

O contrato completo de cada rota (séries, quebras, listas) está em docs/02-contrato-de-resposta.md e em openapi/tdash-v1.yaml.

Customização

Antes de mudar, ache a regra: docs/04-modulos.md lista o fonte e o método de cada indicador, e docs/06-mapa-de-regras.md lista cada regra de negócio, como mudar e o que muda junto.

MudançaSó TLPPPrecisa de versão nova do app
Regra de cálculo de um indicador existente✔
Título, unidade, sentido ou validade de um cartão✔
Colunas, rótulos ou tipos de uma lista existente✔
Painel personalizado (cartões, colunas, barras e tabelas)✔
Indicador novo num painel padrão, nova série, novo módulo✔

Para um processo próprio da empresa, o caminho mais curto é um painel personalizado: não depende de versão nova do app. Indicadores novos nos painéis padrão podem ser sugeridos pelo GitHub ou pelo e-mail de contato.

Mudar a regra de um indicador

Exemplo: o faturamento deve contar também as notas de complemento de preço (D2_TIPO = 'C').

  1. Ache a regra. O faturamento está em TDashFatRepository:salesFrom.
  2. Mude o SQL, mantendo os binds na mesma ordem: 
    // antes
cFrom += " AND D2.D2_TIPO = 'N' "
// depois
cFrom += " AND D2.D2_TIPO IN ('N', 'C') "
    O salesFrom é usado por faturamento, ticket médio, série e rankings: a mudança vale para todos. Se a regra valesse só para um indicador, crie um método novo.
  3. Valor que muda por cliente? Não deixe fixo: crie um parâmetro MV_TD… e passe por bind.
  4. Compile src/fat, rode o smoke test com -Module FAT e confira com o relatório padrão.

Mudar título, unidade, sentido ou validade

Tudo está na linha do catálogo do módulo (função <mód>Catalog() no fonte da API):

{ "fat.revenue", { "kpi", "series" }, "Faturamento bruto", "BRL", "up_is_good", TTL_OP }
//  id (não mude)   tipos               título exibido       unid.   sentido       validade

Se a unidade mudar, o valor precisa estar na nova unidade (PCT exige número de 0 a 100).

Criar um indicador na API

Exemplo: quantidade vendida no Faturamento (fat.items_sold).

1. Catálogo (src/fat/tdash.fat.api.tlpp, função fatCatalog). O id segue <mód>.<nome_em_ingles>:

    { "fat.items_sold", { "kpi" }, "Quantidade vendida", "QTY", "up_is_good", TTL_TAT },;

2. Cálculo (TDashFatApi:kpiValue). Com compare=prev ou yoy, a API chama kpiValue de novo com o período de comparação e calcula a variação sozinha:

        case cId == "fat.items_sold"
            nValue := oRepo:itemsSold(dFrom, dTo)

3. Consulta (src/fat/tdash.fat.repository.tlpp):

/*/{Protheus.doc} itemsSold
Quantidade vendida no período (D2_QUANT), com o mesmo filtro do faturamento (salesFrom).
@type method
@param dFrom, date, início (D2_EMISSAO)
@param dTo, date, fim
@return numeric, quantidade
/*/
method itemsSold(dFrom as date, dTo as date) as numeric class TDashFatRepository
    local nTotal := 0 as numeric
    local oQuery as object

    oQuery := tdash.core.TDashQuery():new(" SELECT SUM(D2.D2_QUANT) TOTAL " + ::salesFrom(""))
    ::bindSales(oQuery, dFrom, dTo)
    if oQuery:open()
        nTotal := ::numberOf(oQuery:getAlias(), "TOTAL")
        oQuery:close()
    endIf
return nTotal

4. Teste:

curl -u USUARIO:SENHA -H "x-erp-module: FAT" -H "tenantid: 01,1001" "https://<servidor>/api/tdash/v1/fat/kpis?ids=fat.items_sold&dateFrom=20261001&dateTo=20261031&compare=prev"

O indicador já responde pela API e pode ser exibido num painel personalizado. Para aparecer num painel padrão do app, ele precisa entrar numa versão do app.

SQL portável e filiais

  • Sempre tdash.core.TDashQuery e bind para valores da requisição.
  • Cada tabela recebe a filial do seu próprio FWxFilial("XXX"), por bind. O tamanho e o compartilhamento da filial mudam de cliente para cliente: nunca fixe tamanho nem valor.
  • Não ligue tabelas de famílias diferentes por A.X_FILIAL = B.Y_FILIAL (ex.: SC1 × SC7). Só entre cabeçalho e itens do mesmo documento (SF2 × SD2).
  • Concatenação com MatiConcat(), nulos com COALESCE, condições com CASE WHEN.
  • Comece os filtros pela filial e pela data, os campos dos índices padrão.

Criar a partir do exemplo

  1. Copie src/custom/tdash.custom.mock.tlpp para src/custom/tdash.custom.<nome>.tlpp.
  2. Troque o nome da classe (TDashCustom<Nome>Api) e a rota do @Get (/tdash/v1/custom/<nome>). Classe e rota precisam ser únicas no RPO.
  3. Troque os valores fixos pelas suas consultas. O tdash.custom.exemplo.tlpp mostra isso reaproveitando as consultas do Faturamento.
  4. Compile (Windows-1252) e teste com curl.
  5. No app: Módulos › Painéis personalizados › Adicionar painel, informe nome, caminho e módulo e toque em Testar.
oPanel := tdash.core.TDashPanelBuilder():new("Meu painel", 300)
oPanel:addKpiTarget("Faturado", nValor, nMeta, "BRL", "up_is_good")
oPanel:addColumnChart("Por mês", "Mês", "R$", "BRL", { "Ago", "Set" }, { { "Faturado", { 10, 20 } } })
oPanel:addTable("Top clientes", { { "Cliente", "" }, { "Valor", "BRL" } }, aRows)
oHelper:setCacheHeaders(300)
oRest:setResponse(oHelper:getResponse(oPanel:getJson()))
  • Módulo: para um dos oito módulos do TDash, o painel só aparece a quem pode ver o módulo. Em Outro, o usuário informa qualquer sigla (ex.: MNT, GFE, TMS) e o REST confere o acesso a cada chamada.
  • Caminho: relativo à raiz do REST; o app recusa outro servidor, .. e #, porque a senha vai junto.
  • Limites: 30 widgets, 10 séries, 60 categorias e 200 linhas; acima disso o app corta e avisa. Prefira agregados a listas longas.

Testes PROBAT

As regras que não acessam o banco (curva ABC, horas da SH6, totalização da visão gerencial, LGPD, painel…) têm testes em tests/. Compile tests/**/*.tlpp num ambiente de desenvolvimento e rode:

appserver.exe -console -consolelog -run=tlpp.probat.run -env=NOME_DO_AMBIENTE

Operação

Publicar uma versão nova das APIs

  1. Compile em homologação: src/core e depois os módulos alterados.
  2. Rode os testes PROBAT e o smoke test com -Module dos módulos alterados.
  3. Compile em produção na mesma ordem.
  4. Se a versão do app também mudou, atualize as APIs antes de os usuários atualizarem o app.

Não é preciso reiniciar nada: o usuário vê o número novo quando a validade do cache vence ou ao tocar em atualizar.

Log

Erros vão para o console.log do AppServer que atende o REST, grupo TDASH, com o contexto Classe:rota (ex.: TDashPcpApi:kpis, TDashQuery:open). O app nunca recebe esse detalhe.
